WB Limits Tracker

Telegram-бот для отслеживания лимитов приёмки на складах Wildberries

Пользователь регистрируется, вводит API-ключ WB, выбирает склады и получает уведомления, когда появляются бесплатные или дешёвые слоты приёмки. Поддерживаются demo-режим (mock API) и production (webhook + real WB API).

// Архитектурные решения

  • Два режима WB API (WB_API_MODE) — mock (JSON-фикстуры, демо без аккаунта продавца) и real (реальные эндпоинты через httpx)
  • Два режима запуска (USE_POLLING) — long polling для dev/demo и webhook через Flask для production
  • Слой абстракции WbClient — бизнес-логика не зависит от конкретной реализации API
  • FSM — пошаговая настройка: ввод API-ключа → выбор складов через inline-кнопки
  • Шифрование API-ключей — хранение ключей в SQLite как enc: + Fernet, миграция legacy plaintext при старте
  • Разделение sync/async — Flask работает синхронно, async_runtime прокидывает корутины aiogram в event loop
  • Scheduler — авто-уведомления только пользователям с подпиской (paid=1), выбранными складами и найденными доступными лимитами

// Что интересного в реализации

Один код — два способа доставки — handlers не зависят от polling или webhook
Mock-слой как подсистема — те же JSON-фикстуры для CI, демо и pytest
Валидация до сохранения — API-ключ проверяется до записи в БД. Пользователь не попадает в «полусломанное» состояние с невалидным ключом
Шифрование на границе репозитория — handlers работают с открытым ключом, user_repository прозрачно шифрует при записи и расшифровывает при чтении. Плюс автоматическая миграция старых plaintext-записей при запуске приложения
is_available в модели — бизнес-правило доступности лимита WB (коэфф. 0 или 1 + allow_unload) инкапсулировано в Pydantic, форматтеры и scheduler не дублируют эту логику
Два UX-канала на одни сценарии — Slash-команды (/check) и reply-кнопки («🔍 Проверить лимиты») ведут к одной бизнес-логике. Меню команд (set_my_commands) и reply-клавиатура дополняют друг друга
FSM + приоритет хэндлеров — Кнопки нижнего меню регистрируются до FSM-fallback'ов, чтобы пользователь мог выйти из сценария выбора складов через «Отмена» или сразу нажать «Проверить лимиты», не застревая в состоянии
Scheduler как отдельный «потребитель» доменной логики — scheduled_check() вызывает check_limits_html() из services и не дублирует код проверки лимитов
Pydantic на границе внешнего API — ответы WB нормализуются в Pydantic-модели, а не пробрасываются в raw-словарь, Это защищает внутренний код от смены формата JSON и даёт типизацию для mypy
Логирование по модулям — логирование вынесено в logs/ по модулям (app.db.log, app.scheduler.log и т.д.). Удобно для production и отладки, не засоряя stdout при polling

// Принципы

  • Separation of Concerns — Telegram UI, бизнес-логика, persistence и внешний API разделены
  • Open/Closed — новый источник данных WB можно добавить как ещё одну реализацию WbClient, не трогая handlers
  • Configuration over code — demo/production переключаются env-переменными, без ветвлений в коде
  • Testability first — mock-клиент, фикстуры, изолированная temp-БД в pytest, CI без secrets продавца

// Возможности бота

  • Регистрация и валидация API-ключа Wildberries
  • Выбор складов через inline-чекбоксы
  • Ручная проверка лимитов (/check) и демо-режим без реального ключа (/demo)
  • Reply-клавиатура и меню команд
  • Автоматические уведомления по расписанию (подписка)
  • Admin-страница со статистикой (в webhook-режиме)
