ReliaPay

Единый банковский контур — проект стажировки ModulDev (Модульбанк)

ReliaPay — backend-система для банковских операций и сценариев оплаты. Задача проекта: собрать один надёжный контур, через который снаружи безопасно принимаются запросы, внутри выполняются операции, а наружу уходят платежи во внешний сервис — с защитой от дублей и возможностью пережить сбой.

Все запросы идут через одну точку входа. Сервис проверяет, кто обратился и корректны ли данные, затем выполняет нужную операцию в базе PostgreSQL. Клиент передаёт только название модуля, действие и JSON с данными. Прямой доступ к SQL и внутренним функциям закрыт — это безопаснее и проще для тех, кто вызывает API.

Python C# / ASP.NET Core PostgreSQL Docker Compose JWT JSON Schema Метрики и мониторинг AI-инструменты

// Что сделано

  • Собран единый контур. Снаружи — входной шлюз (единственный открытый порт). Дальше — API-сервис, который проверяет запрос и запускает операцию в PostgreSQL. Рядом работают фоновые воркеры (шаги сценария) и Python-сервисы, которые общаются с внешним платёжным провайдером.
  • Спроектированы API и правила обмена данными. Вход по токену, проверка тела запроса по схеме, каталог доступных операций, единый формат ответов об успехе и ошибках. Описание API собирается из каталога операций, чтобы контракт не расходился с реализацией.
  • Надёжная обработка операций. Важные изменения в базе проходят в одной транзакции: либо операция фиксируется целиком, либо откатывается. Так не остаётся «половинок» платежа или статуса.
  • Защита от повторных запросов. Если клиент по сети отправил тот же запрос ещё раз — система не создаёт вторую операцию, а возвращает прежний результат. Если при том же ключе пришли другие данные — возвращается конфликт, а не тихий «второй платёж».
  • Интеграция с внешним провайдером. Исходящие сообщения ставятся в очередь, отдельный сервис доставляет платёж, другой принимает подтверждение и возвращает его в систему, третий догоняет сообщения, которые не успели обработаться. Так обмен с внешним миром не ломает основную логику операций.
  • Устойчивость к сбоям. Если упал контейнер или провайдер временно недоступен, работа не теряется: система продолжает с сохранённого состояния в базе. Для проверки можно намеренно имитировать сбои и убедиться, что контур восстанавливается сам.
  • Мониторинг. У запроса есть сквозной идентификатор, можно посмотреть цепочку шагов операции, найти «застрявшие» процессы и снять метрики по очередям — чтобы доказывать исход фактами, а не догадками.

// Архитектура (кратко)

Клиент (с токеном доступа)
    → входной шлюз (единственный порт наружу)
        → API-сервис (права, проверка данных, запуск операции)
            → PostgreSQL (операции, сценарии оплаты, очереди)

Фоновые воркеры      → выполняют шаги сценария
Сервис доставки       → отправляет платёж внешнему провайдеру
Сервис приёма ответа  → принимает подтверждение и возвращает в систему
Сервис сверки         → догоняет сообщения, которые «зависли»

Бизнес-логика и сценарии оплаты хранятся в PostgreSQL, а не «зашиты» в код каждого сервиса. Поэтому новую операцию или сценарий можно добавить без пересборки основных сервисов. Python-часть отвечает за доставку во внешний мир: она не решает, чем закончится операция, и не выбирает ветку сценария — это остаётся на стороне базы и основного runtime.

// Цели надёжности

ЦельКак проверяется
Пережить сбой Останавливаем контейнер или отключаем внешнего провайдера. Система продолжает работу из состояния в базе — без ручного вмешательства в SQL.
Доказать исход Итог операции подтверждается сохранёнными фактами, статусами и метриками — а не тем, что «подождали и надеемся на успех».
